# Feature Specification: Clean Validation & Stabilized Competition Submission Pipeline

**Feature Branch**: `002-clean-submission-pipeline`

**Created**: 2026-09-29

**Status**: Draft

**Input**: User description: "Prepare the repository for a final competition run by: 1. Preserving the current improved pipeline and its behavior. 2. Removing the remaining high-impact validation leakage from the submission path. 3. Ensuring feature selection is strictly fold-local. 4. Preventing OOF overfitting from becoming part of the final submission. 5. Disabling questionable pseudo-label/sharpening components for the final clean run. 6. Fixing any definite runtime bugs that could prevent submission. 7. Keeping the runtime practical on Kaggle. 8. Do NOT introduce broad architectural changes."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Trustworthy Out-of-Fold Validation via Fold-Local Feature Selection (Priority: P1)

As a competitive machine learning practitioner, I need all feature selection and target encoding to occur strictly within each training fold, so that out-of-fold validation scores represent an unbiased, leak-free estimate of test generalization.

**Why this priority**: Global feature selection and unconstrained target encoding leak holdout target information into feature subsets, causing severe over-optimistic cross-validation estimates (e.g., public/local validation divergence) and poor generalization on hidden evaluation data.

**Independent Test**: Can be independently tested by running outer cross-validation where validation partitions and labels are completely isolated from feature selection and target encoding routines, confirming that holdout indices never participate in feature importance, screening, or encoding calculations.

**Acceptance Scenarios**:

1. **Given** training data partitioned into cross-validation folds, **When** feature screening executes for a fold, **Then** only the training fold records and corresponding training targets are used to evaluate and select features.
2. **Given** selected features from the training fold, **When** transformations are applied, **Then** training fold features, validation fold features, and test features are projected using only those fold-selected features.
3. **Given** any target encoding applied in the pipeline, **When** target statistics are computed, **Then** encoders are fitted exclusively on the training fold target and transformed onto validation and test splits without validation target leakage.
4. **Given** the completion of all validation folds, **When** out-of-fold metrics are evaluated, **Then** every single training observation has exactly one valid out-of-fold prediction generated by a model trained without seeing that observation's label.

---

### User Story 2 - Disabling Overfitting Mechanisms and Submission Stabilization (Priority: P1)

As a competition submitter facing a tight deadline, I need speculative enhancements (pseudo-labeling, temperature sharpening, prevalence hacking, and OOF hill climbing) disabled in the final clean submission path, so that final predictions are robust, well-calibrated, and guaranteed not to overfit.

**Why this priority**: Optimizing thousands of blend combinations on the same out-of-fold labels, applying arbitrary probability sharpening (e.g., temperature 0.85), forcing test prevalence scaling, or appending unverified pseudo-labels risks fatal penalties on log loss and ruins test set ranking.

**Independent Test**: Can be tested by running the end-to-end clean pipeline and verifying that final predictions originate directly from regularized model predictions or simple constrained blends without prevalence scaling, sharpening exponents, or test-set pseudo-label injection.

**Acceptance Scenarios**:

1. **Given** raw model probability outputs, **When** generating the final clean submission, **Then** arbitrary temperature sharpening functions and artificial test-set prevalence adjustment multipliers are bypassed.
2. **Given** outer fold training data, **When** model training begins, **Then** training folds contain zero pseudo-labeled test observations.
3. **Given** multi-model out-of-fold predictions, **When** combining model outputs, **Then** either a simple constrained blend or regularized meta-model is used, and iterative multi-round hill climbing searches over the validation targets are avoided.

---

### User Story 3 - Runtime Defect Elimination and End-to-End Execution Safety (Priority: P1)

As an engineer executing the pipeline in a resource-constrained environment (Kaggle notebook under strict time limits), I need all known runtime bugs resolved and a single clean execution entry point, so that a valid submission file is generated deterministically before the deadline.

**Why this priority**: Undefined variable references (such as the `best_floor` reference error in Stage 5 meta-stacker) cause pipeline execution crashes after hours of computation, preventing timely submission file creation.

**Independent Test**: Can be tested by running static code checks and an end-to-end single-seed execution that completes successfully, outputting formatted submission files and complete diagnostic manifests.

**Acceptance Scenarios**:

1. **Given** the Stage 5 meta-stacker routine, **When** final logging and submission generation execute, **Then** all referenced parameters (e.g., floor and alpha configurations) are properly resolved and defined in scope.
2. **Given** the clean execution pipeline, **When** launched under seed 42 with 10 folds, **Then** the process completes within practical time budgets (under 4 hours) on target hardware.
3. **Given** pipeline completion, **When** examining output artifacts, **Then** a valid `submission.csv` is produced matching the required test record count, formatting, and valid probability bounds [0, 1].

---

### User Story 4 - Auditability, Prediction Artifact Preservation, and Run Manifest (Priority: P2)

As an experimenter verifying pipeline integrity, I need raw out-of-fold and test predictions preserved along with an experiment manifest, so that model diversity, leakage status, and configuration are transparently verifiable.

**Why this priority**: Saving raw per-model out-of-fold and test predictions allows independent diagnostic inspection, offline ensembling, and verification that model diversity actually exists without re-running expensive training.

**Independent Test**: Can be tested by inspecting the artifact output directory after a run to confirm the presence of individual prediction arrays and a machine-readable JSON manifest containing run metadata.

**Acceptance Scenarios**:

1. **Given** individual model runs (LightGBM, CatBoost, XGBoost, and optional TabPFN), **When** each model finishes cross-validation, **Then** raw unblended out-of-fold predictions and test predictions are saved to disk.
2. **Given** pipeline execution completion, **When** diagnostics are written, **Then** a JSON run manifest records the Git commit hash, seed, fold count, feature selection counts, and component toggle flags (pseudo-labeling: false, sharpening: false, prevalence adjustment: false).
3. **Given** the final evaluation summary, **When** results are reported, **Then** an explicit LEAKAGE CHECK status (PASS/FAIL) and justification are documented.

---

### Edge Cases

- **Constant or Single-Class Folds**: How does fold-local feature selection behave if a feature has zero variance within a training fold? The selector must drop zero-variance features gracefully without breaking column alignment between train, validation, and test splits.
- **TabPFN Resource Exceeded or Unavailable**: What happens if TabPFN encounters GPU memory limits or excessive runtime? The clean pipeline must cleanly fallback to the core GBDT zoo (LightGBM, CatBoost, XGBoost) without interrupting overall execution.
- **Missing or NaN Features in Test Set**: How does the transformed test set handle features that passed fold-local screening? Missing values must be handled consistently according to the trained model's default requirements.
- **Out-of-Fold Coverage Verification**: What happens if an observation is missed or predicted more than once? The pipeline must perform an explicit boolean mask assertion confirming exactly one out-of-fold prediction per training record.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST perform feature selection strictly inside each outer cross-validation fold using exclusively the training fold indices and training labels.
- **FR-002**: The system MUST guarantee that validation fold data and labels, as well as test set data, never influence feature importance scores, feature rankings, or feature subset screening.
- **FR-003**: The system MUST ensure all target encoding operations are fitted strictly on the current training fold target and transformed out-of-sample onto validation and test sets.
- **FR-004**: The system MUST disable test-set pseudo-labeling in the clean baseline submission path.
- **FR-005**: The system MUST disable arbitrary temperature sharpening (e.g., `temperature = 0.85`) on prediction probabilities in the final clean submission path.
- **FR-006**: The system MUST disable test-set prevalence adjustment multipliers and target mean forcing in the clean submission path.
- **FR-007**: The system MUST replace or disable unconstrained iterative out-of-fold hill climbing in the final clean path, relying instead on a simple constrained blend or regularized meta-model.
- **FR-008**: The system MUST resolve all undefined variable references in `src/stages/stage5_meta_stacker.py` (specifically correcting the `best_floor` reference to use existing configured constants).
- **FR-009**: The system MUST verify that every training record receives exactly one out-of-fold prediction across all cross-validation folds.
- **FR-010**: The system MUST persist raw per-model out-of-fold and test predictions to disk before any downstream blending or post-processing.
- **FR-011**: The system MUST generate a structured run manifest recording Git commit, seed, fold count, feature counts per fold, model configurations, and component enablement flags.
- **FR-012**: When TabPFN is enabled, the system MUST execute genuine foundation TabPFN priors across the two canonical sub-views: `pfn_phys` (14 core physics features) and `pfn_champ` (20 features: physics + channel/digital/bank features) using `ignore_pretraining_limits=True`.
- **FR-013**: The system MUST strictly eliminate any surrogate fallback (such as substituting CatBoost or other decision trees in place of TabPFN). If TabPFN or GPU is unavailable, the pipeline MUST either raise an explicit error or be configured to exclude TabPFN via a transparent configuration flag, never silently falling back to a surrogate model.

### Key Entities

- **Fold Partition**: Encapsulates outer training and validation indices, training fold features, training labels, holdout validation features, and holdout validation labels.
- **Fold Feature Screen**: Represents the set of active column identifiers determined solely from a single fold's training slice.
- **Raw Model Predictions**: The uncalibrated, unblended probability arrays generated out-of-fold for training data and averaged across folds for test data.
- **Run Manifest**: Structured JSON metadata detailing execution parameters, model configurations, feature counts, and pipeline integrity flags.
- **Final Submission**: Formatted output file containing unique test identifiers and predicted class probabilities bounded within [0, 1].

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of feature selection and target encoding steps in the final submission pipeline execute strictly within outer cross-validation loops without observing validation labels.
- **SC-002**: 100% of training samples have exactly one validated out-of-fold prediction (zero unpredicted samples, zero duplicate predictions).
- **SC-003**: The end-to-end clean pipeline executes within 4 hours on standard single-GPU Kaggle environment using seed 42 and 10 folds.
- **SC-004**: Zero runtime crashes due to undefined variables or missing metadata across all execution stages.
- **SC-005**: A valid, complete `submission.csv` is produced with exactly matching test set row counts and all probability values strictly in the range [0.0, 1.0].
- **SC-006**: 100% of individual model raw out-of-fold and test predictions are exported and verified prior to any ensembling.
- **SC-007**: An explicit LEAKAGE CHECK status is documented with PASS verification confirming zero target or validation data contamination.
- **SC-008**: TabPFN foundation priors, when activated, execute genuine TabPFN models across both `pfn_phys` and `pfn_champ` views with 0% surrogate fallback code paths executed.

## Assumptions

- **Target Metric**: The competition evaluation metric combines LogLoss and Area Under the ROC Curve (AUC). Arbitrary probability distortion (sharpening or prevalence scaling) degrades LogLoss significantly despite minor ranking changes.
- **Baseline Architecture**: The Stage 2 GBDT zoo architecture already incorporates fold-local screening concepts and serves as the primary, most reliable backbone for the clean submission path rather than rewriting older stages.
- **TabPFN Architecture**: TabPFN executes genuine foundation priors on GPU across `pfn_phys` (14 features) and `pfn_champ` (20 features). If GPU or TabPFN dependencies are absent, execution is governed by a clean boolean flag rather than an opaque surrogate model.
- **Multi-Seed Strategy**: Multi-seed averaging (e.g., seeds 42, 123, 2024, 3407) is secondary and will only be executed if the initial clean single-seed run succeeds with ample time remaining.
- **Calibration Stance**: In-sample post-hoc calibration will be skipped in favor of raw uncalibrated/natively regularized probabilities unless proper cross-fitted calibration is already in place without runtime penalty.
